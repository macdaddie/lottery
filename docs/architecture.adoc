== Purpose

A Python application that uses genetic algorithms (GAs) to explore frequency-based
prediction of Powerball numbers from historical draw data.  The data is fetched
from a New York State open-data CSV endpoint and stored in a local SQLite database.

[NOTE]
====
Powerball draws are independent random events.  Past frequency data has zero
predictive power for future draws.  This project is an educational exercise in
genetic algorithm design, not a serious prediction tool.
====

== Genetic Algorithm Primer

A genetic algorithm is a search heuristic inspired by natural selection.  Instead
of solving a problem directly, it evolves candidate solutions over successive
generations, keeping the best traits and discarding the worst.

=== Core Concepts

[cols="2,3"]
|===
|Concept |Description
|Population |A set of candidate solutions at a given point in time.
|Chromosome |A single candidate solution, composed of genes.
|Gene      |The smallest building block of a solution (one parameter).
|Allele    |The specific value carried by a gene.
|Fitness   |A score measuring how good a solution is.
|Selection |Choosing parents proportionally to their fitness.
|Crossover |Combining two parent chromosomes to produce offspring.
|Mutation  |Randomly perturbing a gene to maintain diversity.
|Generation|One complete iteration of the evolutionary loop.
|Convergence|The population settles on similar high-fitness solutions.
|===

=== The Evolutionary Loop

. **Initialisation** — Generate a random population of N chromosomes.
. **Evaluation** — Score every chromosome with the fitness function.
. **Selection** — Pick two parents based on their fitness (higher = better chance).
. **Crossover** — With probability `p_c`, splice parents to create offspring.
. **Mutation** — With probability `p_m`, randomly alter each offspring gene.
. **Replacement** — Merge offspring into the population, keeping population size.
. **Termination** — If max generations reached or convergence detected, stop.
Otherwise, return to step 2.

=== Domain Mapping: GA → Lottery

[cols="2,3,2"]
|===
|GA Concept |Lottery Domain |Implementation
|Population  |Set of ticket candidates |`List[Ticket]`
|Chromosome  |One ticket (5 white + 1 Powerball) |`Ticket` class
|Gene        |A single ball number |`Ball` class
|Allele      |The integer value (1-69 white, 1-26 PB) |`Ball.value()`
|Fitness     |How well a ticket matches historical frequency |`FrequencyFitness` function
|Selection   |Pick promising ticket numbers |`TournamentSelection`
|Crossover   |Swap balls between two tickets |`Ticket.crossover()`
|Mutation    |Randomly change a ball value |`Ball.mutate()`
|Convergence |Population clusters around popular numbers |Stagnation check
|===

== GA Process Flow

The core evolutionary loop executed by the GA Engine:

[source,mermaid]
----
flowchart TD
    start([Start]) --> init[Generate random population]
    init --> eval[Evaluate initial fitness]
    eval --> loop{generation < max_generations?}
    loop -- yes --> select[Select two parents<br/>(tournament)]
    select --> cross["Crossover with probability p_c<br/>offspring"]
    cross --> mutate["Mutate each gene<br/>with probability p_m"]
    mutate --> grow[Add offspring to new population]
    grow --> full{new population < pop_size?}
    full -- yes --> select
    full -- no --> replace[Replace old population with new]
    replace --> reevaluate[Evaluate fitness of new population]
    reevaluate --> best[Record best-so-far]
    best --> inc[generation++]
    inc --> loop
    loop -- no --> output[Return best candidate from history]
    output --> end([End])
----

=== Step-by-step Walkthrough

. **Initialisation** — Create `pop_size` random `Ticket` objects.  Each `Ticket`
  contains 5 white-ball `Ball` genes (1-69) and 1 Powerball `Ball` gene (1-26).
  Random alleles are drawn uniformly from the valid range.
. **Fitness evaluation** — For each ticket, look up the historical frequency of
  each of its six numbers in the materialised `frequency` table.  The sum of
  all frequencies is that ticket's fitness score.  (Future: score by prize tier
  instead.)
. **Selection** — Run a tournament: pick `k` random tickets from the population,
  return the one with the highest fitness.  Repeat to get a second parent.
. **Crossover** — With probability `crossover_prob`, splice the two parent
  tickets to produce an offspring.  Crossover is bounded: the resulting numbers
  must remain within `[1, 69]` for white balls and `[1, 26]` for the Powerball.
  If a generated value would be out of range, retry up to `MAX_TRIES` times,
  then fall back to a random valid value.
. **Mutation** — For each `Ball` gene in the offspring, flip each bit in its
  binary representation with probability `mut_rate`.
. **Replacement** — When the offspring pool reaches `pop_size`, replace the
  entire old population with the new one (generational replacement).
. **Termination** — After `max_generations` iterations, return the ticket with
  the highest fitness ever seen (elitism via best-so-far tracking).

== Database Schema

The database stores raw draw records and a materialised frequency table.

[source,mermaid]
----

        INTEGER white_2
        INTEGER white_3
        INTEGER white_4
        INTEGER white_5
        INTEGER pb
        INTEGER multi

    FREQUENCY {
        INTEGER number PK
        INTEGER white
        INTEGER pb

    NAMES ||--o{ FREQUENCY : derives
----

[source, sql]
----
CREATE TABLE IF NOT EXISTS names (
    id        INTEGER PRIMARY KEY,
    draw_date DATE    NOT NULL,
    white_1   INTEGER NOT NULL,
    white_2   INTEGER NOT NULL,
    white_3   INTEGER NOT NULL,
    white_4   INTEGER NOT NULL,
    white_5   INTEGER NOT NULL,
    pb        INTEGER NOT NULL,  -- Powerball
    multi     INTEGER            -- Power Play multiplier
);

CREATE TABLE IF NOT EXISTS frequency (
    number  INTEGER PRIMARY KEY,
    white   INTEGER DEFAULT 0,
    pb      INTEGER DEFAULT 0
);
----

The `frequency` table is a materialised view refreshed after every data load.
It is computed by counting each number's appearances across the `names` table.

== Constraints & Assumptions

=== Data Source

|===
|Constraint |Default
|URL        |https://data.ny.gov/api/views/d6yy-54nr/rows.csv
|Format     |CSV (pandas `read_csv`), columns matched by position
|TTL        |6 hours (configurable)
|Fallback   |Local fixture CSV at `fixtures/powerball_fixture.csv`
|===

=== Genetic Algorithm

|===
|Parameter       |Default |Notes
|Population      |100     |May be tuned; larger = slower, more diverse
|Generations     |1000    |Early termination if stagnation detected
|Crossover prob  |0.8     |Fraction of offspring created via crossover (vs. clone)
|Mutation rate   |0.05    |Per-gene, per-generation probability of bit flip
|White gene bits |7       |Covers range 1–99 (actual range 1–69, clamped)
|PB gene bits    |5       |Covers range 1–32 (actual range 1–26, clamped)
|Selection       |Tournament (k=3) |Deterministic tournament size
|Replacement     |Generational |Full replacement each generation
|Elitism         |Best-so-far |Tracked externally
|===

=== Platform

|===
|Item   |Default
|Runtime|Python 3.11+
|DB     |SQLite 3 (stdlib)
|OS     |Cross-platform (macOS, Linux, Windows)
|===

== Design Decisions

=== TOML over environment variables

A single file is easier to version-control, ship with repo defaults, and inspect
than ad-hoc env vars.

=== Materialised frequency table

Recomputing frequency on every query is O(n) in table rows.  The materialised
`frequency` table reduces each lookup to O(1) and is refreshed incrementally on
data load.

=== Populations instead of single-candidate evolution

The notebook's original approach evolves one candidate at a time — this is
sequential hill-climbing, not a GA.  Population-based search provides the
genetic diversity that makes selection pressure meaningful.

=== Console-first, notebook-compatible

The UI module renders to stdout (progress bars, candidate tables, JSON) so it
works in the terminal and in Jupyter notebooks alike.  A future GUI layer can
be added behind the same `ui.py` interface.
